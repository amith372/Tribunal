# The Tribunal — Specification

> **This file = *what* to build**, written as prose in five parts (per the course's specification standard). It is the source of truth and wins if it and `CLAUDE.md` ever disagree on behavior.

## Part 1 — Goal and reason

The Tribunal is a web app that puts a fictional character on trial. The user writes a charge sheet that names the accused, chooses which of five Game-of-Thrones characters is the defendant, and then casts four advocates — two to defend and two to prosecute — on a Side Select screen where each side holds exactly two. The four are drawn from all five characters, the accused included, so one character sits the case out. Each advocate makes a single statement, in its own voice, arguing its assigned side. Three fixed judges, modelled on the published reasoning of real Israeli Supreme Court justices, then each read the charge sheet and all four statements and return a verdict of guilty or not guilty with their reasoning. The app shows the three verdicts, the majority verdict, and the tokens and price the run spent. As each advocate's statement arrives its avatar moves from idle to thinking to happy; once the four are done the judges deliberate behind loading gavels; the results then appear as five swipeable panels — the final verdict, the three judges (tap to expand reasoning), the four advocates with their side, the token-and-price breakdown, and a closing summary slide. A finished run can be exported as a single self-contained HTML file, and the server keeps a durable copy of every run it finishes — a browser that has watched one can find it again later from a Past Runs screen, listing only the runs it has itself seen.

**The reason we are building it** is to see how real judicial temperaments would judge a fictional case, and how different characters' statements change the verdict; when an unwritten decision arises, resolve it toward making that comparison clear and honest. (As a class project, also resolve toward showing the specification and how we verify the AI.)

The decisions that shape it, each a judgement rather than a recipe:

- Advocates each speak once; there is no debate, and no advocate sees another's statement.
- Everyone reasons only from the charge sheet, the provided character and judge facts, and — for judges — the four statements. Personas set voice and values, never facts, and no outside knowledge of the characters may enter. A needed-but-missing fact is labelled an assumption, never asserted as true. **A name counts as a fact.** The name of a place, house, region, title, army, weapon, battle or event is knowledge from outside the tribunal exactly as much as an event is, and it is the easiest form of outside knowledge to admit without noticing, because a name reads as scenery rather than as a claim. Where something the given text leaves unnamed has to be pointed at, it is described rather than named.
- **The defendant is one of the five characters, and the accused may answer the charge themselves — from a defence seat and from nowhere else.** Four seats are drawn from all five characters, which means one character sits the case out and which side each of the four argues is a separate question from who is cast at all. The accused arguing their own defence is not an edge case tolerated by the rules; it is the ordinary shape of a trial, and it is the casting Part 4's own validation case uses. What stays forbidden is the accused prosecuting themselves, and the reason is that it is not a hard case to judge, it is an incoherent one: an advocate is briefed to argue a side whether or not they would have chosen it, and briefing the accused to argue for their own conviction produces either a confession, which is not an argument, or a performance of one, which is not the defendant. *This reverses the earlier rule that the defendant is never also an advocate.* That rule made a certain sense while the four advocates were defined as "the other four" — it was arithmetic, not judgement — but it excluded the one voice a real tribunal always hears, and it made the canonical case uncastable. The cost of reversing it is that the casting is no longer forced: with five characters and four seats the user must now leave somebody out, which is a real decision where before there was none.
- **The grounding rule outranks the persona, and the prompts say so in as many words.** Several of the five descriptions are adversarial by temperament: one presses whatever helps her side and makes little of whatever does not, another finds the weak point in any position and tests it. Read as licence rather than as manner, that is an invitation to invent, which is the one thing an advocate may never do. So the resolution is written into every advocate's prompt rather than hoped for — spin the facts you were given, reading a motive the worst way, pressing what helps and making little of what does not, and manufacture nothing that you were not given. Twist the reading, never the record. *The descriptions themselves were rewritten to stop doing half the damage*: they used to carry plot — houses, offices, wars, the alleged act's own background — and a persona that arrives holding facts is a fact source no matter what the prompt says about it. They now carry manner, values, distortions and argumentative habit, and nothing else.
- **The judges hear the four statements labelled by side, not by name.** Each is put to them as an argument for the defense or for the prosecution, so that a verdict turns on the argument rather than on the reputation of whoever made it. Advocates write in character and in the first person, so a statement may still name its own speaker; that is left alone, because forcing a character not to name themselves would damage the voice that makes the comparison worth running. The label is anonymous, the writing need not be, and the difference is deliberate.
- **The user casts the sides.** Which two advocates prosecute and which two defend is a deliberate choice the user makes, not one the app assigns — who argues which side is exactly what a run is testing. The Side Select screen holds each side to two, so an invalid split is hard even to express; the server still checks the split independently of what the screen allowed.
- The five characters' descriptions, their relations, and the three judges' personas come from three provided data files and are the only source of character facts. Those files describe *standing relationships*; the charge sheet supplies *what happened*. The two are kept apart, because a data file that states the alleged act as fact would decide the trial before it runs. **The character descriptions carry no plot at all** — no place, house, office, army or event, not even the uncontested ones. The grounding rule would permit them, since whatever a prompt is given is a fact the speaker may use; the point is that it should not have to. A persona holding plot is a second, unchecked account of what happened, sitting beside the charge sheet and competing with it, and an advocate reaching for the version in their own description rather than the one in the sheet is arguing a different case from everyone else. Relations are the deliberate exception and stay as they are: a standing relationship is exactly what a persona is not, and it is the one thing about a character the charge sheet has no business supplying. **The judges' personas adapt method rather than person.** Each is drawn from three of that justice's reported opinions, and the file names them, so a reader can check the temperament against its source rather than take it on trust. They are simulations of judicial reasoning, not portraits and not predictions: nothing here claims any of these people would decide this case, or any case, in any particular way, and the export says so on the record it hands the reader.
- **The charge sheet must name the defendant.** A charge sheet that never mentions the accused leaves the advocates nothing to argue about and would have them invent the case. The match is case-insensitive and on whole words, against the character's given and used names — "Dany" counts for Daenerys — but never against a shared surname: "Lannister" fits Tyrion and Cersei, and "Targaryen" fits Daenerys and the hidden-heir Jon, so a name that cannot identify one character is no evidence the sheet is about them.
- Only free OpenRouter models are used, so a run costs no money. The user toggles between one model for all seven roles and a different model per role — that toggle chooses the **mode only**. The model identifiers themselves are chosen by the developer and live server-side; they are never editable in the app, the browser never sends one, and no request may introduce one. **The app does show which identifiers a run will draw from, and showing is not editing**: the setup screen names them as text, with no field anywhere to type one into, and it reads them from the server rather than from a list kept in the browser — a screen naming a model that is not the one being called would be a quieter lie than naming none at all, and the identifiers change on the host without the app being rebuilt. **This specification states the rule; it does not list the identifiers.** The free roster rotates weekly, so a list written here would be wrong within days, and a reader would have no way to tell whether the prose or the code was the stale one. The rule is: one pinned model for one-model mode, and for per-role mode a pool for the judges and a pool for the advocates, judges taking the stronger pool, the two pools sharing no model between them, and every identifier free. **Each pool holds more models than it has seats to fill**, because a pool the size of its seats has nothing left to offer a role whose model is rate-limited or delisted — and that is the ordinary case, not the rare one. The lineage rule binds what may sit *together*, not merely what may be cast: no two judges should be built from shared weights, whether they arrived that way by casting or by failing over, so the bench prefers a spare from a maker it is not already using. **It is a strong preference rather than a prohibition, because the free roster is too thin to afford the absolute version.** Enforced absolutely it leaves judges with no vetted spare at all, and what a seat falls to then is the free router — an unvetted model resolved by someone else, which is a worse outcome for the same rule. So a different-maker spare is always offered first, a same-maker one is taken only when nothing else remains, and **on the rare run where one actually answers, the record says so** — the same way it discloses two roles that ended up on one model. What must never happen is not a shared lineage but a shared lineage the reader is not told about, because a bench of three reported as independent when two of it were not is a verdict resting on a fact nobody can check. **The roster itself lives in `server/src/config.ts`**, which is the single place it exists; `npm run models:check` reports which pinned identifiers are still live and what is currently free to replace one, and each slot can be overridden by an environment variable on the host, so a delisting costs a configuration change rather than a code change or an edit here. A roster change is a perishable fact and is not logged; a change to the rule above is a decision and is.
- **Models are shuffled within their pool on every run, and no two roles share one.** A fixed role-to-model mapping would confound persona with model capability — if one judge always ran on the largest model, any difference in its verdicts might be the model rather than the judicial temperament, which is the very comparison the app exists to make. Judges keep the stronger pool and advocates the smaller one, since handing a judge a small model would trade one bias for a worse one; within each pool the assignment is random per run. **A pool holds no two models of the same lineage.** Shuffling three judges across models that share a training pipeline is not independence dressed differently — two such judges can agree for reasons that are not judicial at all, and with a majority of three that pair decides the verdict. So the bench is drawn from three separate model families, and the same rule holds for the advocates. **The distinctness holds under failure too**: a role whose model fails is never handed a model already serving another role in the same run, because two judges answering the same prompt on the same model can agree for reasons that have nothing to do with their temperaments — and with a majority of three, one such pair decides the verdict. The one case that cannot be prevented is disclosed instead: the free router of last resort resolves to whatever model it likes, so where two roles did end up on the same one the run still reports, and says so. The results always report which model actually served each role.
- Sizes are stated, and only one of them is enforced. The charge sheet is between 10 and 300 words — a floor as well as a ceiling, because a one-word sheet can name the defendant and pass every other check while leaving the advocates nothing to argue from but invention — and a sheet outside that range is refused before any model call. **The ceiling was raised from 200 to 300** when the canonical charge sheet arrived in the shape a charge sheet actually has: an act alleged, an agreed factual record, and the question put to the tribunal. That is 243 words, and it does not fit in 200. The alternative was a worked example that arrived abridged, which would have made the app's own reference case the one case no advocate could argue in full — and the agreed record is precisely the part an advocate would otherwise have to invent. The cost is real and it is paid on every call: the sheet is quoted into all seven prompts, so a hundred more words of it is a hundred more words seven times over. It is accepted because a charge sheet the advocates can argue from is what the requests are being spent on. The advocate statement's 150 words and the judge's 120 — both raised from 120 and 100 after measurement — are **soft caps**: asked for in the prompt, measured on the way back, and recorded and shown when a reply runs over. Nothing trims a long reply, re-asks for a shorter one, or refuses it.
- Before any model call, the app confirms the run is valid — the defendant is one of the five characters in `characters.md` (a character that is not in the story cannot be the defendant), the defendant is named in the charge sheet, exactly four advocates are cast, each a different character from the roster, split two-for and two-against, with the accused nowhere on the prosecution, and the charge sheet is present, within length, and actually states a charge or asks a question rather than only describing a scene — and refuses an invalid run before spending a single call. It reports every fault it finds at once rather than the first, each saying what is wrong and what to do about it, so a bad setup costs the user one correction and not four. This is a cheap structural check (a roster lookup and a name match), not a model call. **The setup screens show those same checks answering themselves as the case is written**, so a fault is found while typing rather than at the moment of pressing Run — which matters because the daily allowance is rationed in requests, and a refused run is the one kind of mistake that costs nothing to catch early. The screen reads the pre-flight's own rules from the server to do it, rather than keeping a second copy of them that would eventually pass a charge sheet the server then refused. What the screen shows is a preview; the decision is the server's, always, and the two screens' arrangement of the casting is never what makes the split valid.
- The app is in English throughout. It is designed desktop-first and stays usable down to a phone: the result panels advance by on-screen arrows and by keyboard, and by swipe on touch. One thematic visual identity carries every screen, and it is the look of an old case-review console rather than a neutral web app: a bronze frame around a parchment sheet, a deep crimson plate for the masthead and for section bars, cream panels ruled in tan, inscriptional serif display type for the wordmark, headings and verdicts, and a single glossy blue plate for the one primary action a screen offers. It is built on shared design tokens so no screen drifts from the others, and it uses the project's own avatar art: the five characters each in an idle, a thinking and a happy state, and one judge portrait in two states — so the three judges are told apart by the name beside the portrait rather than by the face, which is what the available art allows. The art itself is still: the movement described above is added to it rather than drawn into it, which is also what makes it removable — a reader whose system asks for reduced motion is shown the same screen with every portrait, glow and gavel held still, and loses nothing but the motion.

## Part 2 — Testable success criteria

Each has one true-or-false answer anyone can check:

- Every completed run shows exactly four statements — two for, two against — and three verdicts.
- A run in which an advocate failed to deliver is shown and exported as an incomplete trial, naming which advocate is missing, rather than as a completed run that happens to have three statements. A run in which both advocates on one side failed returns no verdict at all.
- The final verdict equals the majority of the three shown verdicts (3–0 or 2–1). If a judge fails, the result reads Hung (1–1) or Inconclusive, and no verdict is invented.
- Each judge shows exactly one verdict, guilty or not guilty, together with its reasoning. Two distinct reasons is what is asked for and what the app reports against — it shows how many the judge actually gave — but a verdict that arrived with thinner reasoning than that is still shown and still counted toward the majority. Discarding a real verdict over the quality of its prose would be a worse failure than reporting a thin one.
- The token total on the results panel equals the per-call token numbers added up, and the price reads $0 while only free models are used.
- The defendant never appears among the two prosecuting advocates. Where they were cast at all, they were cast to defend; a run that put the accused on the side accusing them was refused before any model call.
- Exactly four advocates are cast, each a different one of the five characters, and exactly one character is left out of every run.
- No model call is made unless the defendant is one of the five characters in `characters.md` and the setup is valid; an invalid setup is refused with a message and zero calls spent.
- A charge sheet that never names the chosen defendant is refused before any model call, and the refusal states which names were searched for, so the user can see why it failed rather than guess.
- A charge sheet shorter than 10 words or longer than 300 cannot be submitted. Every statement and judge reply is measured against its word limit, and one that runs over is recorded and shown as such — the limit is a soft cap, so going over is reported, never prevented.
- A charge sheet that names the defendant but accuses them of nothing and asks nothing is refused before any model call, with a refusal that says what was missing.
- The setup screens' preview of those checks reaches the same answer as the server, on every case in the pre-flight's own catalogue. The screens re-apply the rules so a fault is found while typing, and a preview that has drifted out of step is worse than no preview at all: it encourages a setup the server will refuse, and the user pays a request to find out. Where the two disagree the server decides — but a disagreement is a defect, and it is a defect anyone can check for rather than one that waits to be discovered by a refused run.
- Every model call in a run used a model on the app's free allowlist. A request naming any other model is ignored, and there is no field, setting, or environment variable by which a run can be made to use a paid model.
- The exported record and the results panels describe the same run in the same words. The file's five sections are the panels' five, in the panels' order and under the panels' headings, and the sentences inside them — the finding and its tally, which advocates argued which side, how the calls group into waves, the closing summary and who dissented — are derived once and rendered twice rather than written twice. A disagreement between the two is a defect, and it is one anybody can check for rather than one that waits to be noticed by a reader holding a printout beside a screen.
- The exported record wears the app's own palette, and a colour that changes in one and not the other is a test failure rather than something noticed by eye. The file cannot share the app's stylesheet — it has to open with nothing to link to — so it carries a copy, and a copy nothing checks is a copy that drifts. What makes the duplication safe is that every colour the document uses is held against the design tokens the four screens are drawn from. This is not decoration: Part 3 asks a reader to check the panels against this file, and a record that looks like a different product from the app that produced it invites exactly the doubt it exists to remove.
- A finished run exports as one HTML file that opens from disk with no server and no network, carrying the charge sheet, the casting, the four statements, the three verdicts with reasoning, the per-call model/token/price table and the raw model responses — and its numbers match what the app showed.

## Part 3 — Architectural guidance

The backend holds the OpenRouter key and every prompt, and the browser never sees them; reach all models through a single OpenRouter client, which is also the one place the free-model rule is enforced. Read the character, relation, and judge facts from the three data files and treat them as the only character facts.

**The server archives every finished run, and the exported HTML file is still the record a reader keeps and can submit.** A single user on a private URL was once reason enough to skip a database entirely, but a run that vanished the moment its tab closed was not "nothing to browse", it was "no way to browse it" — so the server now keeps a durable copy of every run it finishes and a past run is reachable again by anyone who holds its id, not only by whoever was watching when it happened. **The listing rule is per-browser, and stated as plainly as the free-model rule: the server archives every run, but a browser lists only the ids it kept for itself.** **And what a browser keeps, it can drop — on the user's say-so and never on the app's.** An id whose run the server no longer resolves is left standing rather than quietly removed, because that list of ids is the only handle any run has: a server pointed at the wrong database, or at none, would answer a whole list with silence, and an app that pruned on that answer would destroy the last pointer to every real run in the time it took to open one screen. So the screen says plainly how many of its ids came back unresolved and offers to forget them, and forgetting is the user's action. A dropped id is unrecoverable by design — nothing else in the world holds it — and that is precisely why it takes a person to do it. There is no query by defendant, by date, or by anything else — a run is not discoverable by anyone who does not already hold its id — which is what keeps a private URL private despite the archive existing at all: knowing the app's address is not knowing a run's id. **What a run is judged on is stored with it, server-side only.** The character relations a run's prompts drew from go into the archive beside the run, so an archived run still says what it actually saw even after `data/relations.md` is later edited — but that data never reaches the browser and never appears in the export, because it was never part of what either was showing. Independent of all of this, each run still produces a self-contained exported document carrying the charge sheet, the casting, the four statements, the three verdicts and their reasoning, the per-call breakdown of model, tokens, price and time, and the raw model responses. It is a file the user keeps and can submit, and it records an incomplete run honestly rather than hiding it — the portable copy of a run, now rebuildable from the archive as well as from a run still in flight, rather than a copy that was the *only* record and expired with a ten-minute hold. **It carries the display face it needs and borrows the rest.** "Opens with no network" and "looks like the app that produced it" pull against each other, because the app's type is served from a font host the file cannot reach; the resolution is to embed the display face used for the wordmark, headings and verdicts, subsetted to what the document actually prints, and to let the reading text fall back to whatever old-style serif the machine already has. The verdict is the thing a reader looks at and the thing a reader is asked to trust, so it should be the thing that matches; body prose in a near-enough serif costs the document nothing, and tens of kilobytes on every exported file to make it exact would be paid on every run forever. **The file is laid out as the results screen is.** It carries the same five sections the panels do, in the same order, under the same headings, and describing the run in the same sentences — the finding, the bench with its reasoning, the four advocates by side, every call the run made, and the closing summary — followed by the raw responses as an appendix, since those have no panel because no screen shows them. This is what turns "check the file against the panels" from an impression into something a reader can do line by line. It also means the wording exists in two places, on two sides of a boundary the app deliberately keeps, so the two are held together by a check rather than by care. **The file is rendered where the record lives, and it reaches the user as a download.** The browser is handed a finished file rather than assembling one, because there is then exactly one builder — the same pure function of the same record that the tests can run without a browser — and because the browser does not hold everything the record needs: the raw response bodies are the server's. It is named for the defendant and for the run's own start, so two exports never land on one another and re-exporting one run twice gives one name. **It is reachable for as long as the archive holds the run — which, once a run has finished, is indefinitely.** The in-flight buffer only ever holds a run for the same few minutes the reconnect above describes; once that hold lapses, the export is rebuilt from the archive instead, so a reader who takes their time over the five panels does not find the download gone at the moment they ask for it, and neither does one who comes back another day. A file already downloaded is unaffected by any of this; it is the record, and it belongs to whoever downloaded it. **The raw responses keep whatever they came with**, links included: they are quoted evidence rather than prose, they are escaped and unreachable inside the document, and editing them to make the file look tidier would be editing the thing the file exists to preserve. **A third, older thing exists beside the archive and the export, and it is not either of them**: a local, ignored file to which each finished run is appended, raw model responses included, because free models fail in ways that cannot be reproduced on demand and a failure with no record of the response behind it cannot be diagnosed at all. It is a developer's debugging log and not a store the app reads from — nothing in the running app reads it back, nothing is rendered from it, no screen can reach it, and deleting it changes nothing about how the app behaves. The archive is the opposite of that on every count: the app reads from it, a screen renders from it, and it is exactly what makes a past run reachable again.

Keep the pipeline stages as plain functions the routing layer calls, so each can be tested without a running server. Leave the file layout, the function shapes, and the export's internal structure to the agent.

**A run is streamed, and it survives the browser letting go of it.** The screen is described in Part 1 as changing while the run happens — avatars moving from idle to thinking to happy as each statement lands, gavels turning while the bench deliberates — so results are pushed as they settle rather than delivered in one silent batch at the end. Each advocate statement and each judge verdict is sent the moment that role settles, and the finished run record closes the stream.

Because a run costs seven requests out of a daily allowance that is rationed in requests, and because nothing is exportable until the run finishes, a browser that drops the connection at second eight would otherwise destroy something expensive and unrecoverable. So **a run is addressable by an identifier, and the server holds it while it is in flight and briefly after it finishes**, so that a reconnecting browser is sent everything that has already arrived and then continues with the rest. This is a buffer, not the archive: it lives in the running process and does not survive a restart, and it is not where a finished run's durability comes from — that is the archive's job, and it exists precisely because this buffer does not survive a restart and was never meant to. What the buffer alone guards against is narrower and immediate: a moment's flakiness costing seven calls and the record with them before the run has even finished.

**The browser keeps that identifier while it is watching a run, and keeps nothing else about the run itself.** The hold above rescues a dropped connection, but not a dropped *page* — and a reload in the middle of a trial is the ordinary way seven requests get spent twice on one case. So the tab remembers the identifier of the run it is watching, for as long as that tab is open, and a page that loads holding one rejoins that run rather than starting another. It is a pointer, not a record: no charge sheet, no statement, no verdict and no total is written into the browser for this, and it is dropped the moment the user leaves for a new case. **A second, longer-lived pointer is what makes the archive screen work, and it is a different thing from this one.** Once a run finishes, the browser also keeps its id in a separate list that survives closing the tab — still only an id, still no charge sheet or verdict written into the browser — and that list, not this one, is what the archive screen reads to ask the server for summaries of runs this browser has seen. The two pointers answer two different questions — "what am I watching right now" and "what have I finished" — and neither one is the run.

**One run produces one record, and everything downstream renders that.** The stage after judging does not decorate the results for the screen; it folds the run into a single object — the charge sheet, the casting, the four statements, the three verdicts, every call that was made, the totals, and the outcome — and the panels, the stream's closing message and the exported file are three renderings of that one object rather than three places that each work the numbers out. This is what makes "the export's numbers match what the app showed" true by construction instead of true by coincidence: there is only one place the numbers exist. The record is built by a pure function of what the earlier stages returned, so a run can be reconstructed and checked without a server, a key, or a browser.

**The outcome is a shape, not a verdict with excuses attached.** A run ends as a verdict with its tally, as hung, as inconclusive, or as aborted before judging — and these are different things, not one thing with a flag. Distinguishing them structurally is what stops a renderer printing a verdict that was never reached: where there is no verdict there is no field to print, so "never invent a verdict" is held by the shape of the data rather than by every screen remembering to check. A majority is two of the three seats, so two agreeing judges carry it even where the third failed; one against one is hung; a single surviving verdict is inconclusive, because one judge is not a bench.

## Part 4 — Validation approach

Before building, commit one known case and check the finished build against it by hand.

The case is **T-001, The Realm v. Jon Snow**: Jon intentionally killed Daenerys Targaryen, stabbing her during a private meeting in the throne room after the fall of King's Landing. The charge sheet is the canonical one — the act alleged, an agreed factual record of five points, and the question put to the tribunal, which is whether the killing was justified as the necessary defence of others and of the realm given what Jon knew, the scale of the threatened harm, the presence or absence of safer alternatives, and his lack of formal authority. It runs to 243 words, which is why the ceiling is 300.

**The casting is Jon and Tyrion defending, Daenerys and Grey Worm prosecuting, and Cersei sitting the case out.** Jon answers the charge himself, which is the point of the lineup and not an oversight — it is what four seats drawn from five characters exist to allow. Cersei is not dropped from the app: she remains on the roster and castable in any run, and this particular case simply does not seat her. The old casting, with Tyrion and Cersei defending, is kept as a second passing case, because a run in which the accused stays silent is still an ordinary run and the rules have to hold for it too.

The tribunal answers *guilty* or *not guilty*, and on this question those are the same two answers as *not justified* and *justified*. It does not sentence, and it does not merge the three opinions into one — the majority is counted and reported, and the three opinions stand as themselves.

Running this case, confirm by eye that: the pre-flight passes (Jon is a story character, he is named in the charge sheet, four advocates are cast from the five, the split is two-for and two-against, and the accused is on the defence rather than the prosecution); four statements appear, each on its assigned side, and Jon's speaks as the accused rather than as a third party discussing himself; three verdicts appear, each guilty or not guilty with at least two reasons; the shown majority equals the count of the three verdicts; and the token total equals the per-call numbers summed, with a price of $0. Then export the run, open the downloaded file from disk with the server stopped, and confirm it renders completely on its own and its numbers match the panels.

Then run the deliberately invalid cases and confirm each is refused before a single model call: a defendant who is not in the story; a three-to-one split; a charge sheet that never names the character chosen as defendant; and **the accused cast on the prosecution**, which is the invalid case the casting rule brought with it — the one arrangement of an otherwise perfect setup that the tribunal will not hear.

## Part 5 — Known pitfalls

Warnings to build against, each written once:

- A judge may return prose instead of the required form — read the verdict from the text, retry the call once, and only then mark it an error; never invent a verdict. Reading it from the text is lenient about form and strict about meaning: a verdict written as prose, as a label, or inside a JSON object that was cut off mid-sentence is still a verdict and is taken. But a reply that supports both readings at once — two verdicts stated, or a lone "guilty" standing under a negation — is treated as unreadable and retried rather than resolved, because choosing between them risks reporting the opposite of what the judge ruled, and that error would pass silently into the majority and the export.
- **A judge's retry stays on that judge's own model and buys no fallback.** The retry exists so the same judge can state its ruling again at temperature zero — not so that a verdict may be obtained from wherever one happens to be available. Letting it fall through to the free router would put another model's answer into the record under a named judge's name, which is not a judge failing but a judge impersonated, and the exported file would carry it as that judge's ruling. So the retry is one call on the same model, and if it fails the judge fails — which the bench already handles honestly, since two agreeing judges still carry a majority and one against one reads Hung. The cost is losing a judge to a momentary rate limit. That cost is accepted, and it is smaller than it looks: the retry follows seconds behind the first call, so a limit that was hitting then is likely hitting still, and the router would often be the only thing able to answer — which is exactly the case where calling it the same judge stops being true.
- A model call may time out, and a free model may be rate-limited (a 429) or delisted without notice — give every call a short fallback chain of free models, retry down it on failure, and keep partial results. A role that exhausts its chain fails as a role; it never borrows a model that is already working for someone else in the run. **Whether the next request goes to the same model or the next one depends on why the last one failed.** A timeout, a provider error, a dropped connection or a malformed body are accidents of a moment, and asking again is the cheapest thing that can clear them — so the role gets one more ask of the model it was cast with before it gives that model up. A model this key is not permitted to use is a third kind again, and it is easy to mistake for a broken key: some models the roster lists as free are gated to particular kinds of application and refuse every request from anything else. That refusal is about the model and not the key — the same key works on the next model in the same run — so it moves on rather than stopping the role, which is exactly what a rejected key must do instead. A rate limit and a delisting are not accidents: a limit that was hitting a second ago is hitting still, and a delisted model does not relist between two requests, so both skip straight to the next model. Asking them again would spend a request from an allowance rationed in requests to be told the same thing. **The single exception is a provider that says how long to wait.** The reasoning above turns on the wait being a guess; a `Retry-After` is not a guess, it is the provider stating what its own pool needs, and where one is sent and is a few seconds long the role waits it out and asks the same model again. This costs no extra request — the retry was going to happen either way — and what it buys is the seat staying on the model it was cast with, which matters most on the bench, where falling through can quietly put two judges on one lineage. It is deliberately narrow: only a rate limit, only where a figure was actually sent, only where that figure is short enough to be a hiccup rather than an outage, and only once per call. A limit that does not clear in the time its own provider named is not going to clear by being waited on twice.
- **A call is bounded and so is the run that contains it, and the second bound is not implied by the first.** A per-call timeout only promises that one request will stop waiting; a run is two sequential waves of parallel calls, so a set of calls that each return just inside their limit can still leave a user watching a stream that has nothing more to say for several minutes. The run therefore carries its own deadline, derived from the shape of a run rather than chosen: two waves, at most three attempts each, at the per-call timeout — **90 seconds a call, 540 seconds a run**. Both are ceilings and neither is a target: three measured runs finished in twenty-six, seventy-seven and a hundred and one seconds. The per-call figure is set above the slowest answer ever observed rather than at a round number, because a timeout that fires on a model which was going to answer costs the wait and a retry both, and the retry is usually just as slow. Reaching it ends the run where it stands and **keeps every partial result**: the roles that answered are in the record as they arrived, the roles that never came back are written in as failures, and the record says the run ran out of time rather than reporting a bench that mysteriously lost some judges. Nothing is emitted behind the closing record — a call that lands after the deadline has missed the run, and its late arrival must not appear after the result.
- **The daily free-model cap is account-wide, and no fallback chain survives it.** A 429 on one model is exactly what the chain exists for. A 429 because the account has spent its day's free requests is a different animal wearing the same status code: every free model is refused at once, so failing over is not resilience but three more wasted requests against a limit that has already gone. The two are told apart by what the refusal says and handled differently — the daily cap stops the run at once and reports itself in plain words, because "try again in a moment" is wrong advice when the answer is tomorrow. The cap rations *requests*, not tokens, which is why a generous token ceiling costs nothing against it while a single retry costs a whole request. At seven calls a run, an account that has never purchased credit gets roughly seven runs a day; measured on 2026-08-21, this project's key is on that fifty-request tier. A demo is planned around that number rather than discovering it mid-trial.
- **The free roster rotates, sometimes weekly.** Identifiers that were live when written have since disappeared entirely, so they are re-checked before a demo — by a script that names which pinned identifiers are gone, which setting overrides each one, and which free models are currently available to replace them — and they are changeable through configuration without touching code. A check that depends on remembering to look is not a check. **And a roster is a list of models that exist, not a list of models that work.** A free identifier can be listed, current and still refuse every request, because the free capacity behind it is a pool shared with everyone else using it — a fact about the provider rather than about this account, and one no amount of retrying here can move. So the running process keeps a short memory of which models have just refused it, and prefers the ones that have just answered: cold models are picked last to fill a seat where the maker has an alternative, and last to serve as anyone's spare. **This changes preference and never permission** — a cold model is still allowed and is still cast where it is the only model of a lineage the bench needs — and it exists to stop the pointless case, where a role is handed as its one fallback a model that another role discovered was refusing seconds earlier. The memory lives in the process, lapses on its own so a recovered model returns without anything being edited, and is forgotten on a restart. A role that fails over reaches for another *vetted* model first, and the free router only when its pool has nothing left to give it — so a mid-run delisting degrades a run instead of killing it, without an unvetted model taking a seat while a vetted one was still available. What the chain does *not* contain is a model already serving another role in the same run: failing over onto one would quietly put two roles on the same model and confound the very comparison the run exists to make. **Spares are assigned across the whole run rather than claimed by each role in turn**, because roles fail together far more often than they fail alone — a rate limit is usually an account-wide moment, not a single unlucky call — and letting the first role take whichever spare it liked would strand a later one that had only that option. A chain is also never longer than the attempts that will actually be made, so it never names a fallback nothing will reach. Because the router resolves to a different model at call time, the results report the model named in the response, never the one requested. **That same fact makes the router the one place a model this app has rejected can still reach a seat**, because the request names the router — which is permitted — and only the reply names what actually answered. A model measured and set aside is therefore checked against the model that *answered*: a resolution to one is refused and the role moves on, at the cost of the request already spent. Without that, an exclusion is a note rather than a rule, and the two failures that prove it are different in an instructive way — one was a classifier that returned no verdict and announced itself, and the other was a code model that wrote fluent, plausible advocacy with none of the character in it, which nothing downstream would have caught and the run record would have carried as that character's own words.
- A charge sheet may lack its actual question — the advocates must not invent the charge; the pre-flight and the prompts should surface a missing question rather than guess around it.
- A free model may ignore the word limit — hold the limit in the prompt, where the models do respect it, and set the token ceiling well above it: high enough to cover the model's thinking as well as its answer, so a reply never truncates mid-form. The ceiling is headroom, not a second word limit; raising it does not lengthen what comes back. **And when a reply is cut off anyway, that is read from the provider's own report of why it stopped, never guessed at from the text.** A severed reply can parse perfectly well and still be half a ruling, so a judge's answer that ended because the ceiling was reached is treated as unreadable — on the retry as much as on the first attempt — rather than having a verdict salvaged out of the fragment. A ceiling that turns out to be too low then announces itself instead of quietly degrading a verdict.
- **A reasoning model spends tokens before it answers, and a ceiling sized for the answer alone truncates it mid-thought.** The strongest free models think at length by default, which slows the run and inflates the token count. Reasoning is therefore asked for at low effort and its text kept out of what comes back — but **that exclusion only holds when the reply finishes.** A call cut off mid-thought has no clean answer to hand back, so it hands back the thinking. Measured on 2026-08-21: an advocate call budgeted at 220 tokens — already generous against its 120-word cap — spent 214 of them thinking and returned the model's own deliberation about how to count words as the statement; the identical call at 1200 tokens finished inside 939, spending 523 on thinking and then producing a clean 103-word statement with no deliberation in it at all. So the ceiling is set above thinking *and* answer rather than above the word count, and the numbers are re-measured rather than reasoned about. The reasoning tokens the API reports are still counted and shown, because they were really spent: a run reports several thousand tokens for a few hundred words of visible text, and that is the honest figure, not an error in the table.
- A defendant may be chosen who is not in the story, an invalid for-against split may be set, or the charge sheet may never name the accused — the pre-flight refuses the run before any call is spent, and refuses it on the server even where the screen would not have allowed it.
- A single judge failing can leave a one-to-one result — show Hung or Inconclusive rather than forcing a verdict.
- A judge may return a verdict with no reasoning at all, or with fewer reasons than were asked for. An empty reasoning is worth one more call; thin reasoning is not worth even that, and neither is worth discarding the verdict over. The ruling was really made, and a run that threw it away would report Hung or Inconclusive for a bench that had actually decided.
- **An advocate's reply goes on screen unchecked, where a judge's does not.** A judge's text passes through a parser that reads a verdict out of it and refuses what it cannot read. Whatever an advocate returns simply *is* the statement — shown to the user, put in front of all three judges, and written into the export as the run record. So a model that answers with its own working, *the user wants a statement as Tyrion, first person, under 120 words, let me draft*, has that stand as a courtroom statement and be judged as one; the verdicts would then be real rulings on text that was never an argument. The reply is therefore screened before it is accepted, on the same principle the verdict parser uses: lenient about style, strict about whether the thing is a statement at all. What is refused is text about the task rather than about the case — the user, the prompt, the word count, the drafting, the model's own nature — together with a reply that arrived empty or was cut off mid-thought. Screening is never rewriting: a refused reply is worth one more call, and if the second is no better the advocate is marked failed rather than patched, because an invented statement is the same error as an invented verdict and the run already knows how to be honestly incomplete. **That second call goes to a different model.** Talking about the task instead of the case is a disposition rather than a formatting slip — unlike an unreadable verdict, which the same model at temperature zero will often render correctly on a second attempt — so the model that produced the refused reply is dropped from the chain and the next one is asked instead. Asking the same model again spends a request from a rationed daily allowance to be told the same thing.
- **An advocate may fail as readily as a judge, and the spec's silence on that is not the same as it being harmless.** One failed advocate is a gap the run survives: judging proceeds on the statements that did arrive, and the run is labelled incomplete. Both advocates on one side failing is not survivable — judges hearing only one side would return a verdict that looks legitimate and is structurally rigged, and the exported file would carry it as a real result. The run stops instead, with an honest error.
- **The charge sheet is up to two hundred words of user text going into all seven prompts.** It is delimited and introduced as evidence — the case being argued — so that anything written inside it that reads as an instruction is weighed as part of the case rather than obeyed.
- **A model field the user can edit is a cost hole, not a convenience.** Anyone holding the URL could type a paid identifier and spend against the owner's key, and the app has no login to stop them. The identifiers stay server-side, and the free rule is enforced where the call is made rather than where it is requested.
